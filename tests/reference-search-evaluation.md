# UIPicks 找图质量评测

## 两种验收分别记录

**程序验收**检查记录缺失、引用错误、硬条件状态、错图取证、重复案例与补查陈述。程序通过不能证明画面观察正确、工具调用真实、需求完整或推荐最好。

**任务质量评测**需要用户或设计评审者实际看图，判断需求理解和可用程度。没有人工判断就保持“待评”；不能把模型生成的分数、结构校验或虚构实验当作质量提升。

## 固定真实任务

从用户实际找图记录中选取一批任务，建议初轮 10–20 条；不要为了新版本选容易的题。每条保存原话、用户确认的硬条件与偏好、任务预算、候选范围、图片快照日期和原始案例链接。已知优秀案例单独标记。不要将这些标注提前展示给执行检索的 AI。

覆盖实际使用过的页面状态，例如有内容与空状态、Web 与 App、多轮与单轮、界面参考与免费源码。不存在某类真实需求时不编造历史记录；可以新增合成压力题，但须单列为合成测试。

旧版和新版使用同一批任务、相同工具和预算；尽可能冻结候选与图片，排除来源变动造成的差异。保留一部分未用于改规则的任务作为复查集。在线实搜无法冻结时保存日期与访问失败，区分检索环境变化和规则变化。

## 人工盲评表

将输出标为随机 A/B 并打乱顺序，评审前不告知规则版本。每条结果保存以下字段，可直接复制为 CSV 表头：

```csv
task_id,output_code,reviewer,rank,candidate_url,hard_condition_ids_failed,usable,reason,known_good_case_missed,correction_rounds,elapsed_seconds,review_status
```

- `usable`：人工判断该图是否可直接用于本次参考，填写 yes/no；未评留空，`review_status=pending`。
- `hard_condition_ids_failed`：实际画面不符合的硬条件 id；通过的记录状态不能替代人工检查。
- `known_good_case_missed`：只针对固定候选范围中已知的合格案例，记录其 URL；没有固定标注集时不计算遗漏比例。
- 每个任务的返工轮次、总耗时只登记一次，避免按图片重复累计。

## 对比指标与解释

| 指标 | 计算方式 | 边界 |
| --- | --- | --- |
| 前三张可用比例 | 已人工判为可用的前 3 张 / 已人工评审的前 3 张 | 同时报实际交付数量，少给结果不能掩盖覆盖不足 |
| 任务命中比例 | 前 3 张至少一张可用的任务 / 已评任务 | 未返回图的任务算未命中；人工未评任务不算通过 |
| 硬条件错配 | 交付中违反硬条件的图数、任务数及具体类型 | 目标是不交付已知错配；视觉误判仍需人工发现 |
| 已知好案例遗漏 | 固定标注集中未发现/未进入前列的合格案例 | 分别报告“没搜到”和“搜到但排低”；不是全网召回率 |
| 返工与耗时 | 每任务纠正次数及耗时中位数，列出失败任务 | 不把更长搜索时间无条件当作更好结果 |

修改规则后先看硬条件和任务可用程度，再比较时间成本；有退化时查看需求映射、未搜到的路径与排序理由，按失败环节修正。评测记录应能追溯到该版本 Skill 与实际图片，不靠回忆打分。

## 当前可复现检查

```sh
node --test tests/check-reference-report.cjs
```

`tests/reference-report-fixture.cjs` 中的 example.org、图片描述和工具引用均为虚构测试数据。它用于验证拦截逻辑，不是完成过的真实找图任务。2026-10-25 的旧/新版行为实验也使用固定虚构观察，只能比较记录与披露行为。真实任务的人工盲评尚待收集，不预填成功率或最优结论。
